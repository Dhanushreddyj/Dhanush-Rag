# ADR-006 — Embedding Model and Vector Index Compatibility Strategy

**Status:** ACCEPTED  
**Date:** 2026-08-07  
**Decision Owner:** Dhanush Reddy  
**Architecture:** Enterprise AI Platform for Real Estate  
**Applies To:** Embeddings, ingestion, retrieval, Qdrant collections/index revisions, and embedding-model changes

## Context

Vector retrieval correctness depends on more than having a working embedding endpoint and vector database. Stored document vectors and query vectors must be produced by a compatible embedding configuration, and the Qdrant collection must use vector/index settings compatible with that embedding output.

The project intentionally allows environment-specific provider implementations: production embeddings use AWS Bedrock Embedding Models, while development embeddings are configuration-driven. Qdrant is the sole V1 vector database. A model/provider change can alter vector dimension, semantic space, normalization assumptions, distance behavior, tokenizer/input constraints, or quality characteristics even when application interfaces remain unchanged.

If vectors from incompatible models are mixed in one logical index, retrieval can silently return poor or meaningless results. Dimension mismatches may fail loudly, but semantic-space mismatches can remain operationally invisible while degrading answer quality.

The platform therefore treats embedding configuration and vector-index identity as a compatibility boundary.

## Decision

**A vector index revision is valid only for the embedding configuration and index schema with which it was built. Incompatible embedding changes require a new index/collection revision and re-ingestion; vectors from incompatible embedding spaces must never be mixed.**

For V1:

- ingestion and query retrieval for one index revision use the same compatible embedding model/configuration family;
- every persisted index/collection revision has an explicit compatibility identity sufficient to determine how it was built;
- compatibility metadata includes, at minimum where applicable: embedding provider/adapter identity, embedding model identifier/revision, vector dimension, distance/similarity configuration, index/schema revision, and chunk/payload schema revision;
- credentials and secrets are never stored in compatibility metadata;
- vector dimension is derived/validated against the configured embedding implementation rather than treated as an unrelated magic constant;
- the selected distance/similarity strategy must be explicitly compatible with the embedding model and Qdrant configuration; this ADR does not invent one universal distance metric for every future model;
- document vectors generated by one incompatible embedding space are never queried using another embedding space;
- switching embedding providers or models requires compatibility evaluation even if output dimensions happen to match;
- same dimension does **not** imply semantic compatibility;
- an incompatible embedding change creates a new collection/index revision and triggers re-ingestion/re-indexing before traffic is moved to it;
- existing index data is not silently mutated in place to represent a different embedding configuration;
- cutover occurs only after ingestion completeness, retrieval correctness, and required evaluation checks pass;
- rollback must remain possible while the previous valid index revision is intentionally retained during a controlled migration window;
- index compatibility is enforced below controllers and is not a FastAPI responsibility;
- Qdrant-specific mechanics remain inside infrastructure/repository boundaries even though Qdrant is the sole V1 vector database.

Exact production Bedrock embedding model selection and the current development embedding model remain configuration decisions. Once selected for a concrete index, their compatibility identity becomes part of that index revision's contract.

## Rationale

### Prevent Silent Retrieval Corruption

Dimension validation alone cannot detect vectors generated in different semantic spaces. Treating the embedding configuration as part of index identity prevents accidental mixing that may otherwise look operationally healthy.

### Safe Provider Evolution

The platform can change embedding models later without pretending old vectors remain valid. Migration becomes an explicit build, validate, cutover, and retire process.

### Development/Production Clarity

Development and production may intentionally use different embeddings, but each environment/index must be internally compatible. Index data is not assumed portable merely because both environments use Qdrant.

### Reproducibility

Compatibility metadata allows engineers to determine why an index exists, which embedding configuration built it, and whether a query path is valid against it.

## Alternatives Considered

### Reuse an Existing Index Whenever Dimensions Match — Rejected

Equal dimensions do not mean two embedding models share a semantic space. This can create silent retrieval-quality failures.

### Mix Multiple Embedding Models in One Vector Space — Rejected for V1

There is no approved requirement for multi-vector or multi-embedding retrieval. Mixing incompatible vectors violates deterministic retrieval semantics and complicates evaluation and migration.

### Update Embeddings In Place During a Model Migration — Rejected as the Default

In-place partial mutation creates a period where the index can contain mixed compatibility states and weakens rollback. V1 uses a new revision and controlled cutover for incompatible changes.

### Hard-Code One Embedding Dimension/Distance Metric Forever — Rejected

These properties belong to the selected embedding/index compatibility configuration. Treating them as permanent architectural constants would unnecessarily couple future model choices.

### Assume Development Qdrant Data Is Production-Compatible — Rejected

Using the same vector database technology does not guarantee embedding, schema, or ingestion compatibility between environments.

## Consequences

### Positive

- prevents silent mixing of incompatible vector spaces;
- embedding migrations become explicit and reversible;
- index state is reproducible and diagnosable;
- development and production can differ without false data-compatibility assumptions;
- retrieval/evaluation regressions can be associated with a concrete index revision;
- model changes do not leak into controller/application business logic.

### Tradeoffs

- incompatible embedding changes require re-ingestion/re-indexing;
- migrations temporarily require capacity for both old and new index revisions;
- compatibility metadata and migration checks must be maintained;
- model upgrades become controlled engineering changes rather than simple environment-variable flips.

## Implementation Impact

This ADR performs **no index migration and no application-code change**.

Later scoped tasks must establish:

1. an application-owned representation of embedding/index compatibility metadata;
2. validation that configured query embeddings are compatible with the active index revision;
3. Qdrant collection/index creation using validated vector dimension and similarity configuration;
4. deterministic recording of relevant embedding and schema revision metadata;
5. a re-index path for incompatible embedding changes;
6. integration tests for ingestion/query compatibility and mismatch failure behavior;
7. evaluation gates for retrieval quality before a migrated index becomes active;
8. operational cleanup rules for retiring old revisions only after an approved migration window.

Implementation details such as exact collection naming, alias/cutover mechanics, production Bedrock embedding model ID, and retention duration are not decided by this ADR unless later promoted as architectural requirements.

## Verification

- Can an engineer identify which embedding configuration built an active index revision?
- Will a provider/model change be checked for semantic/index compatibility rather than dimension alone?
- Can incompatible vectors ever be written into the same active index revision?
- Does an incompatible model change force a controlled re-index?
- Is the active query embedding configuration validated against the active index revision?
- Can a failed migration cut back to the previous known-good revision during the controlled migration window?
- Are secrets excluded from compatibility metadata?

Failure on these checks is an architecture violation unless superseded by a later accepted ADR.
